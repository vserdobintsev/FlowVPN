# Разбор результатов безопасности

[← К политике безопасности](../SECURITY.md) · [Разработка](DEVELOPMENT.md) · [Сопровождение](MAINTAINING.md)

Этот документ фиксирует исходные результаты статического анализа и правила их проверки. Он не является заключением независимого аудита. Состояние предупреждений меняется; актуальные результаты находятся в [Security → Code scanning](https://github.com/vserdobintsev/FlowVPN/security/code-scanning), доступ к общему списку требует соответствующих прав репозитория.

## Включённые проверки

На 6 ноября 2026 года GitHub API подтверждает следующую конфигурацию CodeQL:

| Параметр | Значение |
| --- | --- |
| Настройка | GitHub **default setup**, состояние `configured` |
| Язык | C# (`csharp`) |
| Набор запросов | **Extended** (`extended` в API, `security-extended` в терминологии CodeQL) |
| Модель угроз | `remote_and_local` |
| Расписание | Еженедельно (`weekly`) |
| Runner | Стандартный runner GitHub |

GitHub хранит эту конфигурацию на своей стороне. Отсутствие CodeQL YAML в `.github/workflows` ожидаемо для default setup. При копировании репозитория проверка не включается только от наличия этого документа — её нужно настроить для нового репозитория.

Extended добавляет запросы к основному набору и может давать больше результатов, требующих ручного разбора. Это не основание считать предупреждения ложными. Модель `remote_and_local` включает локальные источники в анализ; для desktop-приложения с повышением привилегий такие границы требуют отдельного внимания. [Настройка CodeQL](https://docs.github.com/en/code-security/how-tos/find-and-fix-code-vulnerabilities/configure-code-scanning/configure-code-scanning) · [Наборы запросов](https://docs.github.com/en/code-security/concepts/code-scanning/codeql/codeql-query-suites).

CodeQL дополняют сборки Release/Preview, локальные самопроверки, NuGet audit и отдельный workflow аудита зависимостей. CodeQL для C# не покрывает всю реализацию sing-box на Go, libcronet, PowerShell-установщик, механизмы Windows и реальные сетевые утечки.

## Проверка и исправления

Первичный разбор выявил границы доверия к локальным путям, которые потребовали усиления. Это не подтверждает удалённую эксплуатацию всех 18 результатов. Источники семи `path-injection` включают известные папки Windows и раскрытие переменных в зарегистрированных App Paths; проверяемые операции — чтение и обнаружение файлов.

Для импорта и обнаружения добавлена общая политика локальных путей: проверка абсолютного DOS-пути до файловых операций, отказ для UNC, пространств device, ADS и сетевых дисков. У корней хранилищ клиентов и меню «Пуск» проверяется отсутствие reparse points в цепочке каталогов. При обнаружении установленного приложения локальные ссылки могут использоваться, но каждое перенаправление проверяется отдельно до обращения к следующему пути.

Проверка этих изменений включает **35 изолированных сценариев**. В отдельном проверочном запуске использован настоящий NTFS junction: строгий корень отклоняет его, а допустимый локальный путь приложения проходит предусмотренную проверку. Проверки не запускали VPN; отдельный опыт с junction не включён в число 35.

Политика путей для чтения не является защитой от всех гонок файловой системы или полноценной песочницей. Поддерживаемые OpenVPN-конфигурации по-прежнему могут явно ссылаться на локальные материалы вне своей папки: каталог конфигурации не объявляется строгой границей доступа.

Для запуска движка подтверждён общий источник десяти предупреждений — локальный аргумент `--root`. В исходных вызовах использовались отдельные аргументы и отключённый shell; внедрение shell-команды или обход UAC не подтверждены. При этом одной проверки хеша открытого файла недостаточно, если каталог по строковому пути может быть перенаправлен после проверки. Это подтвердил безопасный опыт с двумя текстовыми файлами, без запуска исполняемого файла или повышения привилегий.

Изменения закрывают эту проверенную границу следующими способами:

- Во всех конфигурациях путь движка и рабочий каталог его запуска фиксированы как `AppContext.BaseDirectory/core`. Разработческий `--root` выбирает только изолированные пользовательские данные и не влияет на эти пути. В MSIX параметр отклоняется и не передаётся при повышении прав.
- Все семь мест запуска sing-box используют общий `CoreIntegrity.Start`: без shell и без неструктурированной командной строки, с проверкой хешей по встроенному lock-файлу.
- Открытые дескрипторы файлов движка и цепочки каталогов удерживаются на протяжении владения дочерним процессом. Reparse points проверяются по открытым дескрипторам и отклоняются; закрытие сеанса освобождает ресурсы.
- Четыре диагностических запуска также удерживают проверку движка в момент запуска, а не полагаются на уже завершённую предыдущую проверку.

Движок разрешён только на локальном несъёмном диске, без reparse points в своих файлах и цепочке каталогов. Это намеренно исключает UNC, сетевые и съёмные диски, junction, symlink и точки монтирования для размещения движка. Движок не ищется в папке данных, выбранной через `--root`. Ограничения размещения движка не объявляются общей политикой для всех пользовательских файлов. Защита целостности всего приложения в доступной на запись переносимой папке требует отдельной оценки.

Для предупреждения 14 проверен системный путь Проводника и аргумент каталога журнала. Подтверждённой инъекции не найдено. Открытие папки журнала переведено на штатный `Windows.System.Launcher.LaunchFolderPathAsync`: приложение передаёт Windows путь папки, не выбирая EXE и не формируя командную строку. Вызов выполняется из обработчика кнопки в UI-потоке; отказ Windows обрабатывается как ошибка действия. [Контракт Windows API](https://learn.microsoft.com/en-us/uwp/api/windows.system.launcher.launchfolderpathasync).

## Разделение привилегий в 1.4.2

Повышается отдельный служебный процесс установленного приложения. Интерфейс остаётся обычным процессом. Обе стороны локального IPC проверяют процесс, пользователя, сеанс Windows, путь EXE, elevation и nonce. В брокере нет произвольных команд, входных путей файлов или доступа интерфейса к секрету Clash API.

План проходит ограничение размеров и закрытую схему. Конфигурация пересобирается; движок получает JSON через stdin, базы — inline. Вспомогательные чтение, декомпиляция и сохранение журнала выполняются без повышения. Самопроверки покрывают конфигурации OpenVPN/Outline, повреждённые сообщения, лишние поля, границы памяти, повторный сервер и завершение IPC без запуска TUN.

Managed startup hooks отключены в runtimeconfig до `Entry.Main`. Это не заявление об отключении всех CLR profiler/environment-механизмов. Реальный запуск MSIX через UAC, отказ, другой пользователь, авария процессов и сетевые утечки остаются отдельными сценариями приёмки.

Локальный прогон 1.4.2 выполнил **407 проверок**: выпуск и жизненный цикл — 38, обновления — 36, функции приложения — 242, API движка — 7, брокер/IPC/отмена — 84. В функциональные проверки вошли автоопределение подключений, ограниченное чтение файлов, схема JSON, нормализация IDN и различение статических ключей и динамических подписок. Ещё 11 проверок процесса коммитов прошли отдельно. Рабочий MSIX собран и проверен по блокам, встроенным хешам движка и конфигурации runtime. Компиляция C# прошла без предупреждений; Windows SDK сообщил только об отсутствии необязательного инструмента `mspdbcmf.exe` для отдельного пакета символов. Пакет не устанавливался, доверие сертификату не добавлялось, настоящий туннель не запускался.

## Порядок разбора предупреждения

1. Зафиксировать номер, правило, ветку и SHA анализируемого коммита. Проверить, относится ли результат к текущему коду.
2. Просмотреть каждый путь **source → sink**, а не только выделенную строку. Отдельно проверить происхождение данных, выполненные проверки, файловые операции и уровень привилегий.
3. По возможности воспроизвести проблему на синтетических файлах без настоящих ключей, установки сертификатов и подключения VPN.
4. Исправлять границу доверия и добавлять проверку поведения. Не менять код только ради исчезновения подсветки анализатора.
5. После сборки и регрессий дождаться нового CodeQL-анализа нужной ветки. Если результат остался, проверить новый поток данных и покрытие модели.
6. Если результат остаётся, сохранить технический разбор и продолжить проверку границы доверия. Если он признан ложным срабатыванием, обосновать это для конкретного потока данных и условий выполнения. Ручное закрытие ради зелёного статуса и массовое подавление не заменяют такой разбор; общих фраз «это локальный путь» или «тестовый код» недостаточно.

Текущая страница предупреждения GitHub обычно показывает состояние основной ветки; результаты PR или другой ветки проверяются отдельно. [Работа с результатами CodeQL](https://docs.github.com/en/code-security/how-tos/manage-security-alerts/manage-code-scanning-alerts/assess-alerts).

## Что этот разбор не подтверждает

- Отсутствие уязвимостей во всём приложении или его зависимостях.
- Безопасность скомпрометированной учётной записи Windows или компьютера под контролем администратора.
- Отсутствие утечек IPv4/IPv6, DNS и QUIC при обрыве VPN, сне или смене адаптера.
- Проверку настоящей установки, обновления MSIX и поведения UAC на всех поддерживаемых Windows.
- Корректность настоящего перехода через UAC и остановки TUN установленного пакета: локальные проверки брокера не выполняют повышение.

Зелёная сборка, отсутствие ошибок запуска анализатора и отсутствие новых результатов — разные факты. Каждый указывается отдельно в описании PR или выпуска.
