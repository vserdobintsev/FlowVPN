# Участие в разработке

FlowVPN развивается как приложение для Windows с интерфейсом WinUI 3 и движком sing-box. Исправления, воспроизводимые отчёты об ошибках, улучшения интерфейса и документации принимаются через issues и pull requests.

Уязвимости обсуждаем непублично — порядок описан в [SECURITY.md](SECURITY.md). Для вопросов об установке и использовании есть [SUPPORT.md](SUPPORT.md).

## С чего начать

1. Проверьте существующие issues и открытые pull requests.
2. Для заметного изменения поведения сначала опишите задачу в issue: кому оно поможет, что изменится и какие ограничения нужно учесть. Небольшое исправление можно сразу предложить в PR.
3. Создайте fork и отдельную ветку от `main`.
4. Подготовьте окружение по [инструкции разработчика](docs/DEVELOPMENT.md).
5. Сделайте связное изменение, проверьте его и откройте PR в `main`.

В один PR лучше включать одну задачу. Переименование файлов, форматирование всего проекта и обновление зависимостей не стоит добавлять к исправлению ошибки без необходимости. Черновой PR подходит для работы, по которой ещё нужна обратная связь.

## Язык и имена

Пользовательский интерфейс, документация, описания issues и PR — на русском. Идентификаторы кода, имена веток, сообщения коммитов и заголовки PR — на английском.

Ветки именуются по задаче, например:

```text
fix/profile-selection
feat/application-presets
docs/installation-guide
chore/update-dependencies
```

`main` — основная ветка. Постоянная ветка `develop` и отдельная ветка для каждого выпуска по умолчанию не нужны. Ветки поддержки создаются, только если появляется отдельная линия сопровождения.

## Коммиты и заголовки PR

Используем [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/):

```text
<type>(<scope>): <description>
```

`scope` необязателен. Заголовок **и всё тело сообщения коммита** пишутся на английском. Краткое описание начинается с глагола, описывающего изменение, без точки в конце. В теле можно пояснить причину и существенные ограничения. Имена людей в корректных строках `Co-authored-by: Имя <email>` сохраняют исходное написание.

| Тип | Когда использовать |
| --- | --- |
| `feat` | Новая возможность |
| `fix` | Исправление ошибки |
| `perf` | Измеримое улучшение производительности |
| `refactor` | Изменение структуры кода без изменения поведения |
| `docs` | Документация |
| `test` | Проверки и тестовые данные |
| `build` | Сборка и зависимости |
| `ci` | GitHub Actions и автоматические проверки |
| `style` | Форматирование без изменения поведения |
| `chore` | Прочие задачи сопровождения |
| `revert` | Отмена изменения |

Примеры:

```text
fix(profiles): preserve selection after deleting a profile
feat(presets): add extension groups
perf(processes): reuse executable metadata during refresh
docs(installation): explain certificate renewal
ci(release): verify package contents before signing
```

Несовместимое изменение обозначается `!` после типа/области или пояснением `BREAKING CHANGE:` в конце сообщения. Опишите, что должен сделать пользователь для перехода. Conventional Commits задаёт формат истории; сам по себе коммит не публикует выпуск и не изменяет версию пакета.

Заголовок PR оформляется так же, как коммит и содержит не больше 120 символов. Для `scope` используйте строчные латинские буквы, цифры и при необходимости `.`, `_`, `/` или `-`. При squash merge GitHub берёт английский заголовок PR и оставляет тело итогового коммита пустым (`BLANK`). Русское описание PR в коммит не копируется. Если при слиянии нужно добавить пояснение вручную, оно тоже должно быть на английском.

## Качество изменения

- Сохраняйте существующий стиль C# и настройки `.editorconfig`. Предпочитайте понятные имена и небольшие методы; оптимизацию подтверждайте измерениями, если она влияет на алгоритм или выделение памяти.
- Не выполняйте блокирующую работу в потоке интерфейса. Для длительных операций учитывайте отмену, таймауты и освобождение ресурсов.
- Для исправления ошибки добавляйте воспроизводимую проверку, если она проверяет поведение, а не повторяет реализацию. Для правки текста достаточно проверки отображения и ссылок.
- Для изменений WinUI проверьте светлую и тёмную темы, узкое окно, масштабирование, фокус клавиатуры и доступные названия элементов. Приложите обезличенные снимки, когда это помогает проверить результат.
- Для маршрутизации и импорта проверьте совместимость с закреплённой версией sing-box. Не ослабляйте валидацию конфигурации, проверку TLS, ограничения размера или таймауты ради принятия одного примера.
- Изменения формата настроек должны учитывать существующие профили. Опишите миграцию и поведение при ошибке чтения.
- Не смешивайте состояние приложения и тестовые данные. Самопроверки выполняйте в отдельной папке; изменение реальной сети должно быть отдельной осознанной проверкой.

Команды сборки и проверок описаны в [DEVELOPMENT.md](docs/DEVELOPMENT.md). В PR укажите, что запускали и какой результат получили. Если проверка недоступна, напишите это явно — не отмечайте её как выполненную.

GitHub Actions проверяет заголовок и сообщения новых коммитов (`Conventional title`), а также сборки двух редакций (`Build (Release)` и `Build (Preview)`). Проверка сообщений отклоняет кириллицу в заголовке и теле, кроме корректных строк `Co-authored-by`; она не определяет язык текста автоматически. Уже опубликованная история в эту проверку не входит. Выпуск подписанного пакета выполняется отдельным workflow; обычному PR закрытый ключ подписи не нужен.

## Конфиденциальность и поставка

Не добавляйте в репозиторий реальные OpenVPN-конфигурации, ключи Outline, PFX, пароли, `settings.dat`, рабочий `runtime.json`, дампы, журналы или каталог `data`. Примеры должны содержать синтетические данные. Публичный `Assets/FlowVPN.cer` — ожидаемая часть поставки; он не содержит закрытого ключа.

Прежде чем отправлять скриншот или фрагмент журнала, проверьте имена пользователей, пути, адреса серверов, токены и сетевые адреса. Обновление зависимостей сопровождается проверкой lock-файлов и лицензий. Изменения подписи, установщика или workflow выпуска требуют отдельного внимания к доступу к ключам.

Порядок выпуска и работы с сертификатом — в [RELEASING.md](docs/RELEASING.md). PR не должен устанавливать пакет, добавлять сертификат в доверенные или подключать VPN в CI.

Общение регулируется [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md). Решения по изменениям принимает сопровождающий проекта; публичный PR не означает обещание принять изменение или выпустить его к определённой дате.
